Tracks the six verification criteria for 19 Bot. Everything that could be done
in code is done; the remaining items are Developer Portal actions that only the
account owner can perform.

## 1. Move the app into a Team

Per the [Teams documentation](https://docs.discord.com/developers/topics/teams),
Team membership requires 2FA first, so do criterion 6 before this one.

1. Enable 2FA on your Discord account (User Settings → My Account).
2. Go to <https://discord.com/developers/teams> and click **New Team**.
3. Open the app's **General Information** page and click **Transfer App to
   Team** at the bottom.

> **This is irreversible.** The docs state that once transferred, an app
> "*cannot* be transferred back." Confirm the Team name is right first.

Team roles, for reference:

| Role | Can do |
|---|---|
| Owner | Everything, including destructive actions. One per team. |
| Admin | Everything except destructive team actions. |
| Developer | View app details, reset tokens, configure endpoints. |
| Read-only | View team and app information. |

Note that **every team member gets access to every app the team owns**, so keep
the team small. A team can hold up to 75 applications.

### One item to consider before submitting

This is outside the literal scope of criterion 2, but a reviewer will see it.

On join, the bot DMs every new member an unsolicited "SECURITY ALERT" naming a
specific real person by username and user ID, labelling them a "Discord TOS
Violator • Stalker • Troll". Criterion 2 covers the app's name, description,
commands, and role metadata, so this does not technically breach it. However,
mass-DMing every new member content that targets a named private individual sits
close to Discord's Community Guidelines on harassment, and it carries a real
defamation exposure for you personally, independent of Discord.

**This remains enabled and unchanged.** It is your call, not a decision to make
on your behalf. It is now controlled by one environment variable, so you can
turn it off without a code change:

```
SECURITY_NOTICE_ENABLED=0
```

If you want to keep a warning but reduce the exposure, two lower-risk options
are: state the behaviour without the labels ("this user has been removed from
this server; we do not recommend engaging"), or move it from an automatic DM
into the rules channel where members read it by choice.

## 3 & 4. Terms of Service and Privacy Policy

Both documents are written and published as real web pages.

- Source of truth: [`docs/TERMS_OF_SERVICE.md`](TERMS_OF_SERVICE.md) and
  [`docs/PRIVACY_POLICY.md`](PRIVACY_POLICY.md)
- Published pages: `site/terms.html` and `site/privacy.html`, generated by
  `scripts/build_legal_site.py` and served by GitHub Pages

The Privacy Policy is written to satisfy the Developer Terms of Service
requirement that it "clearly, accurately, and fully describes to users of your
Application what data you collect, how you use and share such data with us and
third parties, and how users can request deletion of such data." It documents
every database table, states plainly that message content read for link-blocking
is never stored, and covers `/archive` explicitly.

### Why the first attempt was rejected

Discord returned:

```
Validation errors: terms_of_service_url: The Terms of Service URL provided is not allowed.
```

This was **not** a blocked domain. Discord fetches the URL, and the repository
was private, so it received a 404:

```
404  https://github.com/HadithCritic/19--Bot/blob/main/docs/TERMS_OF_SERVICE.md
404  https://raw.githubusercontent.com/HadithCritic/19Embed/main/docs/TERMS_OF_SERVICE.md
```

"Not allowed" is Discord's wording for a URL it cannot reach. Any publicly
reachable HTTPS page is accepted, which is why the fix is publishing the pages
rather than switching hosts.

### Publishing: fresh public repository

The plan is to delete the existing GitHub repository and push the current tree
to a brand new public one with no history. That is the right call, and not only
for tidiness. `scripts/preflight_public.py` reports what the old history holds:

```
245 sensitive file(s) exist in past commits.
   207  log file                            logs/messages_2025-*.json, bot.log, ...
    22  virtual environment                 .venv/Scripts/*.exe
    11  SQLite database with member data    bot_data.db, profanity_strikes.db, role_history.db, ...
     1  environment file with credentials   .env
```

The 207 log files include daily message-log JSON, which is archived member
message content. Publishing the existing history would expose all of that along
with the Discord token and the DeepL key. A single-commit repository removes
every one of them in one step.

### Pre-flight check

Run this immediately before pushing to a public remote:

```bash
python scripts/preflight_public.py
```

It inspects what git would actually publish rather than the filesystem, so an
ignored file is correctly treated as absent. It checks tracked paths against a
list of things that must never be committed, scans tracked file contents for
credential shapes, and reports anything sensitive in reachable history. Exit
code 0 means safe to publish.

### Steps

**1. Rotate the credentials first.** The old values are in the old history, and
deleting a GitHub repository does not un-leak anything already cloned, forked,
or cached.

**2. Confirm the working tree is clean.** `.env` is gitignored and untracked, so
it stays local:

```bash
python scripts/preflight_public.py
```

Expect a clean tree and a dirty history. The next step fixes the history.

**3. Replace local history with a single commit.**

```bash
git checkout --orphan fresh-start
```

```bash
git add -A
```

```bash
git commit -m "feat: 19 Bot moderation and utility application"
```

```bash
git branch -D main && git branch -m main
```

**4. Re-run the pre-flight.** It should now print `PASS`.

**5. Delete the old repository on GitHub**, create a new **public** one, then
point this folder at it and push:

```bash
git remote set-url origin https://github.com/HadithCritic/19--Bot.git
```

```bash
git push -u origin main
```

**6. Enable Pages:** repository **Settings → Pages → Source: GitHub Actions**.
The committed `.github/workflows/pages.yml` builds `site/` and deploys it.

**7. Confirm the pages are live** and return HTTP 200:

```bash
curl -sI https://hadithcritic.github.io/19--Bot/privacy.html
```

**8. Paste the URLs into the Developer Portal** under General Information:

```
https://hadithcritic.github.io/19--Bot/terms.html
https://hadithcritic.github.io/19--Bot/privacy.html
```

### If the repository gets a different name

Both policy URLs derive from a single config value, so only that changes:

```
LEGAL_SITE_BASE_URL=https://hadithcritic.github.io/<new-repo-name>
```

Or edit the default in `core/config.py`. To move to your own domain later, set
the same variable to e.g. `https://wikisubmission.org/19bot`, or override
`TERMS_OF_SERVICE_URL` and `PRIVACY_POLICY_URL` individually.

## 5. Install link

Developer Portal → **Installation**. Either:

- **Discord Provided Link** — uses your Default Install Settings and is limited
  to the `bot` and `application.commands` scopes, which is all this bot needs.
- **Custom URL** — an OAuth2 authorize URL with explicit scopes and permissions.

Recommended Default Install Settings for this bot:

- **Scopes:** `bot`, `application.commands`
- **Permissions:** the set in the next section

Since this bot serves one guild, set **Installation Contexts** to Guild Install
only and leave User Install off.

## 6. Verified email and 2FA for all team members

Every member of the team needs a verified email address and 2FA enabled. Discord
requires 2FA merely to join a team, so in practice this means checking that each
member has confirmed their email. Keep the team to accounts you control until
verification is granted.

## Permissions the bot actually needs

Computed from what the code calls. Requesting only these looks better to a
reviewer than requesting Administrator.

| Permission | Bit | Needed by |
|---|---|---|
| View Channels | `1 << 10` | Everything |
| Read Message History | `1 << 16` | Link blocking, `/archive` |
| Send Messages | `1 << 11` | Announcements, warnings, replies |
| Embed Links | `1 << 14` | Every embed the bot posts |
| Attach Files | `1 << 15` | `/debate` diagrams, welcome image |
| Manage Messages | `1 << 13` | Deleting new-member links |
| Manage Roles | `1 << 28` | New Member and Unverified roles |
| Kick Members | `1 << 1` | Removing unauthorised bots |
| Ban Members | `1 << 2` | After-ban enforcement |
| Moderate Members | `1 << 40` | `/ptimeout` |
| Manage Threads | `1 << 34` | Listing private archived threads for `/archive` |

The bot's role must sit **above** any role it needs to act on. Discord only
permits kicking, banning, and timing out members whose highest role is lower
than the bot's highest role. Administrators are additionally exempt from
timeouts entirely, which `/ptimeout` now detects and reports rather than
silently doing nothing.

`Mention Everyone` is **no longer required**, since `/gqs` was removed.

## Privileged intents

Both privileged intents this bot uses are genuinely required. If asked to
justify them during review:

**Message Content (`1 << 15`).** The bot deletes links posted by members holding
the New Member role. That requires reading the text of messages the bot was not
mentioned in, which is exactly what this intent gates. The documented
alternatives do not apply: slash commands, context menus, and modals cannot
observe messages the bot was not invoked on. Message content is inspected in
memory and never stored.

**Server Members (`1 << 1`).** The bot acts on `on_member_join` to kick
unauthorised bots, re-ban users on the after-ban list, flag newly created
accounts, and assign the New Member role. This intent gates that event. The
documented REST alternatives are lookups by ID, which cannot substitute for
being notified that a join happened.

Note the thresholds: a review is triggered at 10,000 users, and verified apps in
100 or more guilds must have privileged intents approved during verification.
This bot serves one guild, so neither currently applies.

## Reproducing the language audit

```bash
python -c "
import asyncio, main
from discord import app_commands
async def go():
    bot = main.SubmissionBot()
    await bot.db.connect()
    for e in main.EXTENSIONS: await bot.load_extension(e)
    for c in sorted(bot.tree.walk_commands(), key=lambda x: x.qualified_name):
        print(c.qualified_name, '|', c.description)
        if isinstance(c, app_commands.Command):
            for p in c.parameters: print('   ', p.name, '|', p.description)
    await bot.db.close()
asyncio.run(go())"
```
